# session-migrate

DSH（DeepSeek Harness）的**会话迁移**插件：把工作区里的会话备份成可移植的目录，也能从备份恢复。

面板位置：**设置 → 会话迁移**。

---

## 功能

- 按工作区列出会话，并标出每个会话相对上次导出的状态：`未导出` / `无变化` / `有变化` / `新增`
- 勾选会话后导出到 `$DSH_HOME/session-migrate/exports`
- 从备份目录导入（按 sha256 校验后拷贝；已存在的会话被备份覆盖）
- **路径映射重定位**：备份来自另一台机器时，会话的 `cwd` 在本机可能不存在——这些会话不属于任何工作区，在 DSH 里是"隐身"的（数据在磁盘上却哪儿都看不到）。它们会被列进**未关联工作区**，填一个目标路径即可一键重定位（改写 header 的 `cwd` + 搬到新位置 + 注册工作区），目标路径记进 `selection.json` 里该组会话自己的记录，**下次导入自动套用**
- 把已归档的会话取消归档
- **删除单个会话**：数据连同投影缓存一起清掉。入口只出现在**未勾选**的会话上（勾选代表"要保留/导出"，那一批不摆删除入口），并且需要点两次确认
- 删除整个工作区（连同它的会话与投影缓存）
- 把导出目录**上传到百度网盘**的 `AI/exports`，或从那里**获取**回来（逐文件、保持目录结构，命中秒传不重传）

---

## 安装

插件以 profile bundle 的形式加载。最省事的方式是把它链接进目标 profile：

```bash
dsh plugin --profile web add link:/absolute/path/to/session-migrate
```

手工方式等价于两步：

1. 让 profile 能解析到这个包——在 `$DSH_HOME/profiles/<profile>/node_modules/` 下建一个指向本仓库的链接（Windows 用 `junction`，macOS/Linux 用软链）。
2. 把包名加进 `$DSH_HOME/profiles/<profile>/package.json` 的 `dsh.profile.bundles` 数组。

`cordis.patch.yml` 会把插件行插入 profile 的层栈；`package.json` 的 `dsh.client` 声明则让浏览器半边在 web GUI 里加载。

## 界面

面板分三块：

| 分区 | 内容 |
|---|---|
| **工作区状态** | 本机已注册的工作区。未导出（还没有备份）的整组沉底，同类内部按显示名称字母排序 |
| **未关联工作区** | 会话的原始工作区目录在本机不存在（典型情形：备份来自另一台机器）。每行带一个目标路径输入框，以及 `检测重定位是否有效` / `应用重定位` 两个按钮；检测会把问题逐条摊开（目标不是目录 / 目标已注册 / 映射冲突 / id 冲突 / 上级目录不可建） |
| **无工作区会话** | `cwd` 为空的会话（DSH 自己的 orphan），天生合法、不需要映射 |
| **百度网盘** | 面板最底下。登录百度网盘，再把本地备份推到网盘 `AI/exports` 或拉回来 |

> 重定位**通常当场生效**：插件会清掉 DSH 对该会话的 header 缓存，让归属立即重建，不必重启。只有在缓存刷新失败时才会退回"需要重启"，界面上会明确提示。

## 备份目录结构

```
$DSH_HOME/session-migrate/
├── exports/
│   ├── index.json                                        # 备份索引 = "上次导出了什么"（唯一记录）
│   └── sessions/<projectDir>/<sessionSegment>/<fileName> # 逐会话的日志副本
├── selection.json                                        # 会话分组 + 各自的重新映射目标
├── baiduclound.json                                         # 百度网盘应用凭证（用户自己维护，插件只读）
└── baidu.json                                            # 百度网盘登录态 + 探测到的应用根目录
```

**只有两份状态文件，且互不重复**：`exports/index.json` 描述"备份里有什么"，`selection.json` 描述"本地要处理什么"。面板上的 `未导出 / 无变化 / 有变化 / 新增` 全部从这两份派生，没有第三份副本。

> 早期版本还有一份 `export-snapshot.json`，它是 `index.json` 的冗余投影（会话 id 要存三遍、`size` 还要在 fingerprint 之外另存一遍）。现在已废弃：如果你目录里还留着它，可以直接删掉，插件不会再读也不会再写。

`selection.json` 是一组记录，每条只有两个成员：

```json
{
  "groups": [
    {
      "cwd": "D:\\restored\\legacy-project",
      "sessionIds": ["session-df127430-..."]
    },
    {
      "cwd": "D:\\Codes\\Unitys\\2026\\HorizontalHero",
      "sessionIds": ["session-6eba56c8-..."]
    }
  ]
}
```

- **`cwd`** 是这组会话**该落到哪个工作区路径**：没配重映射时就是它的真实 cwd，配过之后就是目标路径。**始终写下来**，导入时按 session id 读到它就能直接落位，不必再靠"会话自己的 header"去推断。（只有连 header 都读不出来的会话才可能是 `null`。）
- **`sessionIds`** 是组内的会话

**没有"工作区主键"**：会话属于哪个工作区，它自己的 header 里写着；原 cwd 在重定位时现读即可。所以查一条会话该落到哪儿，**按 session id 就能查**——这也是为什么未关联工作区里那些会话能"自己记住"用户给它配的目标：用户填完路径、验证通过、点应用，这条记录就随之建起来了。

旧格式都会自动迁移：`{"selected":[id,...]}` 按会话 cwd 归组、更早的 `{"workspaces":{...}}` 丢掉主键只留两个成员、早期单独存放的 `relocations.json` 会被读进来合并一次（之后不再写它）。

`index.json` 是自包含的：`import` 只依赖它和同级文件，因此整个 `exports/` 目录可以直接拷到另一台机器使用。每条会话**只记不可派生的字段**：

```json
{
  "format": "dsh-sessions-export",
  "version": 4,
  "exportedAt": 1790379750664,
  "sessions": [
    {
      "id": "session-df127430-...",
      "cwd": "D:\\Codes\\AI\\sessions-import",
      "fileName": "session.v3.jsonl.zstd",
      "hash": "18E2FDF1E0AF08EE6C19A66F55B0F760546AE293089389EC0357D0272CA03FE4",
      "remoteHash": "18E2FDF1E0AF08EE6C19A66F55B0F760546AE293089389EC0357D0272CA03FE4",
      "fingerprint": "170185253:17451448556166485:405:1790362469098339400:1790362469098339400",
      "archived": false
    }
  ]
}
```

- **`cwd` 必须留着**：目录名反解不回它（见下条）
- **`size` 不存**：就是 `fingerprint` 的第 3 段
- **`createdAt` / `parentSession` / `agentPreset` / `origin` 不存**：它们从没被读过，而且会话自己的 header 里本来就有，导入后宿主会重新读
- **`remoteHash` 记的是「云端那份内容的 hash」**：上传成功后才等于 `hash`，从没传过则是 `null`。它只服务于增量上传（见「百度网盘同步」），不参与导入
- **目录名一律不存**：`projectDir` 是 `projectKey(cwd)` 的**有损编码**——`D:\a-b\c` 和 `D:\a\b-c` 会编成同一个 `--D-a-b-c--`，超过 251 字符还会被截断，所以它既反解不回 `cwd`，自己又完全可以现算。更要紧的是：DSH 的 `assertStoredIdentity` 就是按**当前**规则校验"日志与路径是否相符"的，沿用备份里记的旧目录名反而会被判成不符。`sessionSegment` 同理（对 `session-<uuid>` 恒等于 `id`）

读取兼容 v2/v3：旧索引里的 `projectDir` / `sessionSegment` / `relativePath` 一律忽略，落位现算；缺少 `remoteHash` 时当作「没传过」（下次上传会传一遍，之后自愈）；备份文件按现算路径找不到时，按键名扫一遍 `exports/sessions/*/` 兜底，所以旧规则生成的备份照样能导入。

## 设计说明

- **导出是整体覆盖**：每次导出都会先清空 `exports/`，并用本次选择重写 `index.json`。所以分批导出不同工作区时，先前的备份会被覆盖——这是有意设计，`exports/` 始终代表"最近一次导出"。需要多份备份就先把 `exports/` 整个目录复制出去。
- **指纹与宿主 fs 服务同形**：`index.json` 里的 fingerprint 是 `dev:ino:size:mtimeNs:ctimeNs`，与 DSH 自身 `ctx.fs` 的 `version` 语义一致，因此备份可以在插件版本之间复用，不会因为升级插件就全部显示"有变化"。**大小就藏在第 3 段里**，所以索引不必再单独存一份 `size`（面板上的"变化量"也是从它解析出来的）。
- **判定"有变化"用的是文件版本**（设备号 + inode + 大小 + 高精度 mtime/ctime），不是内容哈希——因此极快，且不会误报。
- **导入会覆盖**：同一会话的现有数据会被备份内容替换——这才是"恢复/回滚"的语义（否则导入只能补缺失的会话，回滚不了任何改动）。新增与覆盖的数量在结果里分别列出，覆盖后该会话的投影缓存会被清掉，让宿主按新内容重建。
- **备份损坏会被拦住**：导入前逐个比对 `index.json` 里的 sha256，不匹配的条目直接跳过，不会用坏文件覆盖好数据。
- **导入会自动补建目录区域**：目标机器上 `sessions/<projectDir>/<sessionSegment>/` 可能根本不存在，原工作区目录也可能不存在——这恰恰是"要从备份恢复"的典型情形。导入会按需创建目录后再写入；工作区目录同样会被补建出来再注册归属。若原工作区路径在当前机器上压根不可能存在（例如把 Windows 的 `E:\...` 备份恢复到 macOS），会话文件仍会写回磁盘，但归属挂不上，结果里会单独报出这个数量。
- **导入会并入勾选**：恢复出来的会话自动进入当前勾选列表（并入而不是替换，不会清掉你原有的勾选），因此导入后可以直接对它们再导出，不必回去逐个勾。
- **工作区列表按两级排序**：先按备份状态排——未导出（还没有备份）的整组沉底；同类内部再按显示名称字母排序（大小写不敏感、数字按数值比较，所以 `item2` 排在 `item10` 前面）。打开面板先看到的就是已有备份、需要处理的那批。
- **配置会自我收敛**：读取 `selection.json` 时，凡是指向已不存在的会话（磁盘上的日志文件没了）的条目会被直接删除并写回文件；导出时选中的会话若已消失则静默跳过。因此配置里不会残留无效项，也不会出现失败占位或错误条目——`index.json` 只描述**实际导出成功的内容**。
- **没有成员的记录会被丢掉**：重映射是"跟着会话"的，没有会话就永远不会被命中。清理只按"磁盘上还有没有日志文件"判断；读不出 header 的会话会被单独放一组而不是丢弃——勾选是用户的选择，不该因为读不出 header 就消失，等下次读得出来会自动归位。
- **"配过重映射"的判据是 `cwd` 与真实 cwd 不同**：记录的 `cwd` 平时就等于会话的真实 cwd，只有用户配过目标（或在未关联区点过应用）之后才会变成别的路径；未关联工作区的列表正是按这个差异来判断"这组有没有配过映射"。
- **未关联工作区 vs 无工作区会话**：这是两个不同的东西。`cwd` 为空的会话是 DSH 自己的 orphan（**无工作区会话**，天生合法、不需要映射）；`cwd` 有值但本机没有那个目录、或该路径未注册为工作区的会话，才是**未关联工作区**，需要配映射重定位。
- **重定位只改第一帧**：会话日志是「一帧一段 JSONL」的多帧 zstd，header 单独占第一帧。重定位只重新压缩并替换第一帧（改 `cwd` 一个字段），**其余帧逐字节保留**，会话内容零改动。
- **重定位当场生效，通常不必重启**：DSH 把每个会话的 header 缓存在内存里，文件搬家后缓存里的 `cwd` 还是旧的，`attachSession` 拿它去校验必然失败——这才是"必须重启"的表象根因。插件在重定位后会主动清掉这些缓存，`attachSession` 随即重新扫描磁盘读到新 header，归属当场重建。这些缓存字段没有公开 API，所以是 best-effort：拿不到就退回"需要重启"（界面会提示）。
- **重定位后还会自动补登记**：DSH 的工作区归位只在**首次初始化**时跑一遍，运行期搬动文件不会补，所以插件启动后也会补登记一次，作为兜底。
- **同一个会话只存一份**：DSH 遇到"同一个 id 出现在两个项目目录"会**直接拒绝启动**（硬报错）。所以导入时会清掉该 id 在别处的旧副本（包括同一份索引里重复出现的），并报告 `deduped` 数量。
- **写 header 时连带注意**：会话 header 有必需字段（`createdAt`、`isSeeded`、`delegationDepth` 等），缺字段的日志会被 DSH **静默跳过**（不是报错）——手工构造会话文件时尤其容易踩到。

## 跨机器循环迁移（Windows ⇄ macOS）

插件就是为"两台机器轮流用"设计的。典型循环：

```
Windows 导出 ──同步──▶ Mac 导入 ──▶ Mac 上继续用 ──▶ Mac 导出 ──同步──▶ Windows 导入 ──▶ …
```

### 同步时只带这一样东西

**整个 `exports/` 目录**（`index.json` + `sessions/`）。它自带 sha256 校验，整体拷贝即可，可以直接拷到另一台机器用。

**不要同步 `selection.json`**：它是**每台机器各自的**状态，记的是"这些会话在本机该落在哪个工作区"。Mac 那份记 Mac 路径、Windows 那份记 Windows 路径——正因为如此，两边各自导入对方备份时才不会把会话放到对方机器的路径上。互相覆盖反而会把本机记住的落位弄丢。

### 每台机器上会发生什么

**首次导入**：所有会话都会进**未关联工作区**——备份里记的是另一台机器的路径，本机没有那个目录。给每个工作区填一个本机路径，点"检测重定位是否有效"通过后点"应用重定位"即可。**每个工作区只需做一次**，之后导入会自动落位。

**之后导入**：

- **已有会话** → 自动落回本机对应的工作区（另一台机器的路径会被忽略，改用本机记住的路径）
- **在另一台机器上新建的会话** → 同样自动落位。备份里同一个工作区的会话共享一个 `cwd`，只要这个工作区里有**任何一个**会话在本机配过落位，同一工作区里其余会话（包括新出现的）就能跟着推出目标——不必把同一个映射反复手工配一遍
- **只有"本机从来没有任何会话的全新工作区"** 才需要手工配一次。那时你提供的确实是新信息，配一次是应该的

**导入后状态会自动变干净**（"已导出"）。导入会把文件拷回工作区，带着新的时间戳，而索引里记的 `fingerprint` 是导出那一刻的——不处理的话你会看到满屏"有变化"，但那显然不是你的改动。所以导入结束时会把这些新版本回写进索引（只改 `fingerprint`，`hash` / `remoteHash` 不动，因为恢复的就是同一份内容）。

> 顺带一个平台差异：Windows 的 `copyFile` 会**保留源文件的时间戳**，所以纯粹"导出 → 导入"闭环里版本本来就不会变；真正让它变的是中间那一环——从云端下载会把文件重新写过。这也意味着这个问题只在"走了一趟网盘"之后才暴露出来。

### 导入是"恢复"语义，会覆盖

同一个会话在本机已有的改动会被备份内容替换，**没有合并**。如果你在两台机器上**都**动过同一个会话，后导入的那份赢。导入结果里的"覆盖 N 个"就是这个数量——真在意的话，导入前先把本机当前状态导出一份留底。

### 导入后一个会话都没进来？

看界面上有没有"有 N 个会话被跳过"。最常见的原因是**只同步了 `index.json` 而漏掉 `sessions/` 目录**——那时会逐条报"备份目录里找不到这个会话的日志文件"。另一个原因是文件在传输中损坏，会报"文件内容与索引记录的哈希不符"。

## 百度网盘同步

面板最底下有两个按钮：**上传到百度云** / **从百度云中获取**，把本地导出目录与网盘上的 `AI/exports` 双向同步。

### 落点在哪里

**默认是 `/apps/<你的应用名>/AI/exports`，不是根目录下的 `/AI/exports`。**

这不是插件的选择。百度网盘开放平台硬性规定：第三方应用只能访问它自己的 `/apps/<应用名>/` 目录，网页端个人空间里的 `/AI` 是应用无权触碰的。面板会把当前生效的真实路径显示出来，免得你去根目录里找一个不存在的东西。

落点本身**可配**，写在 `baiduclound.json` 的 `RemotePath` 里（见下节），两种写法都支持：

| 写法 | 例子 | 行为 |
|---|---|---|
| 相对路径 | `AI/exports` | 拼在应用目录后面。不必关心应用叫什么名字，应用名仍会自动探测 |
| 绝对路径 | `/apps/dsh/AI/exports` | 直接指定，**连应用目录都不用探测**（少一次请求）。路径必须以 `/apps/` 开头，否则会提前报错而不是等 API 给一个含糊的 42213 |

留空则用默认的 `AI/exports`，所以不配也能用。面板上会标明当前路径**来自配置还是默认值** —— 否则你改完配置看到路径没变，会以为是没生效。

### 首次使用：登录

前置条件是 `baiduclound.json` 已经放好（见下节「应用凭证」）。

1. 点「登录百度网盘」，插件向百度申请一个**设备码**
2. 面板显示 8 位用户码、验证地址（`https://openapi.baidu.com/device`）和二维码
3. 在浏览器里打开它，用百度账号登录并输入用户码
4. 面板轮询到授权完成会**自动**变成已登录——不需要手动刷新，也不必填回调地址

用设备码模式而不是授权码模式，是因为授权码模式要求 `redirect_uri` 预先在控制台登记，而本插件跑在你自己的桌面上：既没有固定端口，也没有公网可达的回调地址。

`access_token` 有效期 30 天、`refresh_token` 有效期 10 年。插件在到期前 10 分钟自动刷新，所以正常情况下**只需要授权一次**。

### 同步是怎么做的

**逐文件、保持目录结构**，网盘上能看到真实的 `index.json` 与 `sessions/` 层级。

- **上传**：递归扫描本地 `exports/`，每个文件走百度网盘的三段式上传（预上传 → 分片上传 → 创建文件）。大于 4MB 的按 4MB 分片。**命中秒传的分片一个字节都不会重传**，所以同一个备份重传几乎瞬间完成。全程用 `rtype=3`（覆盖），重传不会产生 `index (1).json` 这种副本。

  > 秒传的判据是 `precreate` 返回的 `block_list`（「还缺哪几片」）为空数组，**不是** `return_type`。而且 `create` **永远都要执行**：文件真正落到网盘上才算数，它报 `-8`（文件已存在）才是秒传成立的证据。
- **上传是增量的**：开始之前先列一次云端目录，**内容没变的会话直接跳过**（判据见下节）。跳过多少会在结果里报出来——不然「点了上传却几乎瞬间结束」会让人以为什么都没做。
- **两端保持一致，包括删除**：上传会把**云端多出来**的文件和目录删掉，获取会把**本地多出来**的删掉。方向永远是「被同步的那一方以源为准」（见下节）。
- **上传结束会核对一次**：再列一遍云端目录，逐个核对，并报出「云端缺少什么 / 云端多出什么」。任何一项对不上就报失败——假成功比失败更危险。
- **`index.json` 一定最后上传**：它是「这份备份完整」的标志。先传会话、最后传索引，中途失败时网盘上留下的是一份能对得上号的旧备份，而不是半个新备份。上传成功后会先把各会话的 `remoteHash` 写回本地索引，**再**传 `index.json`，两端那份索引才会带着一致的上传状态。
- **获取**：先全部下载到 `$DSH_HOME/session-migrate/.baidu-incoming/`，**全部成功之后**才清空本地 `exports/` 并替换过去。任何一个文件失败就原地放弃、本地保持原样——边下边覆盖的做法在断网时会留下「一半新一半旧」的备份，那比不更新危险得多。
- 获取的语义是**以云端为准**：本地多出来而云端上没有的文件会被清掉，连点文件也不例外（普通清空会保留点文件，这里刻意不保留——留下云端没有的东西就不叫一致了）。
- 单个文件失败不中断整批，结果里会列出失败明细；重跑一次即可补齐。

### 增量：怎么判断「这个不用再传」

索引里每个会话有两个内容哈希：

| 字段 | 含义 |
|---|---|
| `hash` | 本地这份导出内容的 sha256（导出时算的） |
| `remoteHash` | **云端那份**内容的 sha256；上传成功后写成当时的 `hash`，从没传过就是 `null` |

跳过上传要**同时**满足三条，缺一条都可能造成假同步：

1. `remoteHash === hash` —— 索引记得这份内容传过
2. 云端确实还有这个文件 —— 它可能被人手动删了
3. 大小对得上 —— 换过落点、或者那个位置被别的内容占了

第 2、3 条不是多余的谨慎：只信 `remoteHash` 的话，把 `RemotePath` 换到一个空目录后，插件会认为「全都传过」而一个都不传。所以每次上传前都会先列一次云端目录，**实际看一眼**。

`remoteHash` 会跨导出保留，但要跟着内容走：内容没变就继承，内容变了就归零（云端那份已经不是这个版本了）。丢了它增量就会永远失效——每次导出都变成全量重传。

### 两端一致：删除是同步的一半

| 方向 | 源（权威） | 目标 | 多余的一方 |
|---|---|---|---|
| 上传到百度云 | 本地 `exports/` | 云端 `RemotePath` | 云端多余的**会被删除** |
| 从百度云中获取 | 云端 `RemotePath` | 本地 `exports/` | 本地多余的**会被删除** |

删除**只发生在 `RemotePath` 之内**——那是用户在 `baiduclound.json` 里明确指出归本插件管的地方，别处一根手指都不碰。删除清单（最多 20 条）会显示在结果里。

> **这是破坏性行为，用之前请确认 `RemotePath` 指向的确实是备份专用目录。** 如果它指向的是一个你还在里面放别的东西的目录，那些东西会在下次上传时被清掉。

获取方向本来就先清空本地再落盘，所以天然一致；上传方向的删除是后补的——早期版本只做增改，云端多出来的会话会一直留着。

> 同步的是 `exports/`，**不含 `selection.json`**。后者是每台机器各自的状态，理由和「跨机器循环迁移」那一节说的一样。

### 应用凭证

凭证**不在代码里**，只从 `$DSH_HOME/session-migrate/baiduclound.json` 读。理由很直接：AppKey / SecretKey 等同于账号身份，谁能拿到它，谁就能以这个应用的名义向用户索要授权；写进源码就等于写进版本库，一次 push 之后再也收不回来。

这个文件由你自己维护，插件**只读不写**——不会生成它，也不会覆盖它：

```json
{
  "AppID": 124380810,
  "AppKey": "你的 AppKey",
  "SecretKey": "你的 SecretKey",
  "SignKey": "你的 SignKey",
  "RemotePath": "/apps/dsh/AI/exports"
}
```

**只有 `AppKey` 和 `SecretKey` 是必需的**，其余三项都可以留空，或者整行删掉：

| 字段 | 必需 | 作用 | 不填会怎样 |
|---|---|---|---|
| `AppKey` | **是** | OAuth 的 `client_id`：申请设备码、用 `device_code` 换 token、30 天后刷新 token，全靠它 | 面板直接报「应用凭证缺少必填项：appKey」，**一个网络请求都不会发出去** |
| `SecretKey` | **是** | OAuth 的 `client_secret`：换 token 与刷新 token | 同上，报缺少 `secretKey` |
| `AppID` | 否 | **xpan 开放接口不读它**。它是控制台里的应用编号，OAuth 流程用的是 AppKey | 无影响 |
| `SignKey` | 否 | 属于**早期 PCS API** 的签名机制；xpan 用 `access_token` 鉴权，不做签名 | 无影响 |
| `RemotePath` | 否 | 网盘落点 | 回退到默认 `AI/exports` |

所以最小可用配置只有两行：

```json
{ "AppKey": "…", "SecretKey": "…" }
```

不过建议都留着——就几十字节的事，而 `AppID` 将来换接口或接别的开放能力时很可能派上用场，真删了还得回控制台找。

> **换授权方式也省不掉这两个。** 不管用授权码、简化还是设备码模式（扫码本身就属于设备码模式），申请设备码和换取 token 这两步都必须带上 `AppKey` / `SecretKey`。原因很简单：它们回答的是「**是哪个应用**在请求授权」，而扫码回答的是「**用户怎么表示同意**」——两者不在一个层面上。设备码模式只是把「用户同意」做成了扫码 + 用户码两种途径，应用身份这一环一步也少不了。

字段名照抄控制台就行：比对时会**忽略大小写与下划线**，`AppKey` / `appKey` / `app_key` / `APP_KEY` 是同一个东西；`AppID` 写成数字或字符串都认；首尾空白会被去掉，但密钥内部的空白原样保留。

`RemotePath` 的两种写法见上一节「落点在哪里」。它和凭证放在同一个文件里，是因为两者都属于「这个应用该怎么用」的配置，而且都是私密的、由你自己维护的东西。

文件缺失、内容不是合法 JSON、或缺必填项时，面板会直接说清是哪一种情况（并给出期望的文件路径），而且**一个网络请求都不会发出去**。改完不必重启，面板下次刷新就会重新读取。

登录态另存于 `$DSH_HOME/session-migrate/baidu.json`（`access_token` / `refresh_token` / 过期时间 / 探测到的应用根目录）。删掉它等于退出登录。

### 出问题时看哪里

界面上的报错**会带上百度返回的 errno 与响应原文片段**——开放平台的错误码表并不完整，而且同一个 errno 在不同接口下含义并不一致，把原文摊开比笼统说一句「请求失败」有用得多。响应形状和预期不符时（例如某个接口没返回你以为一定有的字段），原文同样会一并带出来。常见的几个：

| errno | 含义 | 怎么办 |
|---|---|---|
| `-6` | access_token 无效或已过期 | 「退出登录」再重新登录 |
| `-9` / `-3` | 文件或目录不存在 | 确认网盘上的 `AI/exports` 是否还在 |
| `-10` | 云盘容量不足 | 清理网盘空间 |
| `42213` | 目录不在应用可访问范围内 | 确认应用已通过开放平台审核，且落点在 `/apps/<应用名>/` 下 |
| `42216` | 请求过于频繁 | 稍等再试；插件已内置重试与指数退避 |

应用**必须先通过开放平台审核**才能使用网盘基础服务。没通过时，登录可能成功但一列目录就报权限错误——那是账号侧的状态，插件这边改不了。

### 排查用的原始记录

每次上传或获取都会把请求/响应摘要写进 `$DSH_HOME/session-migrate/baidu-debug.log`（覆盖写，只留最近一次）。参数位置、返回字段这类问题在界面上说不清，那份文件里有原文——里面**不含 access_token**。

界面上的报错同样会带上响应原文。这不是装饰：`filemetas` 那个字段名（`list` 还是 `info`）就是靠错误信息里打出的原文一眼认出来的，而在此之前它只表现为一句「网盘没有返回这个文件的下载信息」。

### 关于"网盘里看不到文件"

落点 `/apps/<应用名>/AI/exports` 在网盘**网页端显示为「我的应用」文件夹下的目录**，不是根目录。找不到时先在网页端确认「我的应用」（`/apps`）里有没有你的应用名。

但更值得留意的是另一种情况：**目录在网页端根本不存在**。那通常意味着创建目录的那次调用其实没生效——插件现在会在建完目录后立刻列一次确认，建不出来就直接报错，不会再带着一个不存在的目录往下走。

## 架构

| 文件 | 角色 |
|---|---|
| `host.js` | 宿主半边：注册 `sessionMigrate` 远程服务（18 个 direct 方法），负责所有文件、查询与同步编排 |
| `baidu.js` | 百度网盘开放平台的协议层：OAuth 设备码、分片上传与秒传、递归列举、下载。不碰文件系统，凭证也一律由外部传入，因此可以用假 fetch 完整测试 |
| `client.js` | 浏览器半边：在 `settings.section` 槽位注册面板，通过 typert Remote 调用宿主 |
| `cordis.patch.yml` | bundle 补丁：把插件行插入 profile 层栈 |

两侧通过 `@deepseek-ai/dsh-typert-protocol` 的 Remote 协议通信。

### 宿主依赖

必需：`sessionQuery`、`workspaceRegistry`。
可选：`dshHomePath`（决定 `$DSH_HOME` 位置）、`sessionPersistence`（导出前 flush 落盘）。

**文件操作全部走 `node:fs`**，不依赖 `shell` 服务，因此 Windows 与 macOS 行为一致，也没有 PowerShell 的进程启动开销。

### 已踩过的坑

前两处在协议升级时都会**静默**失效，值得记一笔；后几处是百度网盘和删除功能那边真金白银踩出来的：

1. **客户端命名空间是异步安装的**。`ctx.remote.$mount(contribution)` 返回后才存在 `ctx.remote.<namespace>`，且新版客户端不再用 Proxy 做惰性查找。在 `apply()` 同步阶段取快照会永远拿到 `undefined`，必须在调用前 `await mount`。

2. **宿主只认原型上的稳定字符串键描述符**（`@deepseek-ai/dsh-typert-protocol/remote-methods`）。协议包 ≤ `0.1.0` 把标记存在模块私有的 `WeakMap` 里，而 `@deepseek-ai/dsh-typert-protocol` 这个说明符很可能被别的插件 hoist 到 profile 顶层——于是插件的标记写进了旧副本的 `WeakMap`，宿主的 `collectSrcClaims()` 读原型却什么都没有，端点最终以 **HTTP 404** 收场。

   因此 `host.js` 现在**不继承任何第三方基类**，直接用 `ctx.reflect.provide()` 按 Cordis 契约注册服务，并按新约定手工写描述符；对旧宿主的 `WeakMap` 标记则通过 best-effort 的动态 `import` 补写，缺失也不影响运行。

3. **上传链路的三个接口都必须带 `openapi=xpansdk`**（`precreate` / 分片上传 / `create`）。少了它，`precreate` 会返回 `{"errno":0,"return_type":1,"block_list":[...]}`——errno 是 0、形状像「秒传」，但**没有 `uploadid`**，云端也没有建立任何上传任务。整个上传静默失败，界面上却一路显示成功。这个坑的特征很好认：那时 `block_list` 会被**原样回显成 MD5 字符串数组**，而正常应该是分片序号数组。官方 Go SDK 把该字段注明为「上传链路需要携带」。

   顺带一提，POST 的业务参数会同时在 query 与 form body 里各放一份——服务端读哪边都不会丢，这是排查这个坑时顺手加的保险。

4. **`return_type` 不能用来判断秒传**。官方 SDK 把它注释成「系统内部状态字段」，实测中即使文件已存在也可能返回 1。真正该看的是 `block_list`（还缺哪几片），而最终是否成立由 `create` 决定——所以 `create` 在任何情况下都要执行，它报 `-8`（文件已存在）才算秒传。上传结束后还必须列目录逐个核对文件是否真在云端：只比数量不够，「已上传 5 个文件」加「网盘上现在有 0 个文件」这种自相矛盾的结果，曾经被当成绿色成功显示出来。

5. **`filemetas` 的响应字段是 `list`，不是 `info`**。官方 Go SDK 的结构体写的是 `json:"list"`，而部分文档示例写的是 `info`。只认其中一个的后果是「从百度云中获取」**整体失败**：每个文件都报「网盘没有返回这个文件的下载信息」，看起来像权限或路径问题，其实只是没读懂响应。现在两个都认，成本为零。

   顺带：百度的 `fs_id` / `request_id` 是 64 位整数（实测 18 位），超出 JS 的安全整数上限 2^53。多数值上 `String(Number(x))` 的最短往返表示恰好还原原值、看不出问题，但那是运气，所以解析时就把超过 15 位的整数字面量按字符串保留。

6. **会话查询是"派生索引"，不会因为文件被删就自动收敛**。`ctx.sessionQuery` 背后是 SQLite（`dsh-session-query-sqlite`），它只在**搜索**时才与持久化对账（`_reconcile` 里算出 `persistentDeletes` 再删行），而 `listSessions` / `filterSessions` 是**直接读库**的。所以删掉会话日志之后，那些会话仍会被查询原样返回——面板上就表现为"删了还在"，而且**搜一下它才消失**。

   结论：插件自己的列表一律**以磁盘为准**。`dropMissingSessions()` 会用 `scanSessionLogs()` 过滤掉查询结果里"磁盘上已经没了"的会话，`listGroups` / `listSessions` / `export` 三处都接了它。

7. **活跃会话不会重建工作区索引**。`workspaceRegistry.readSessionHeader` 对**正在对话的那个会话**会先命中 live 分支、拿到 header 就 `return`，根本不会走 `listStoredHeaders` + `indexHeaders` 那条重建路径。所以"清掉索引缓存等宿主自己重建"这招对它无效——`sessionPaths` 会一直空着，该会话被 `sessionIds` getter 过滤掉，在侧栏里以"路径不认识"的形态掉进「未分组」。

   正确做法是**直接写宿主的索引表**（`syncSessionIndex()` 里 `sessionPaths.set` / `delete`），而不是清掉等重建。`realpath` 的结果与宿主的 `realpathNormalize` 一致。
